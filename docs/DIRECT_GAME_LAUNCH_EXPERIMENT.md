# Experimental Direct Launch enabled for live testing (October 27, 2026)

**Direct Launch is enabled for real Windows gameplay testing.** The former unconditional `require_ready()` error was removed; the Rust preflight checks only the installed game and client runtime files. The worker then attempts the actual Stage 2 service startup, verifies the installed game-side SteamCompat/Stage2Trace DLLs and catalog, and launches Evolve. Missing dependencies or failed service startup produce diagnostic errors, not an arbitrary feature lock. Client Launch remains selectable as a fallback.

The services-only host remains **experimental and not yet confirmed through gameplay**; enabling the test path is not proof of runtime parity. The manager does not bypass actual missing files or unresolved original-file backups. Static inspection of the client provides the following background: Static inspection of the user-provided Modded Evolve installation and its October 25–26 launcher logs gives the following process-creation contract:

1. Finish game/runtime preparation and start client-owned **local TLS profile services** at loopback port 2000 and plain services at 2040.
2. Establish the session-specific identity, profile data, compatibility provider and relay selection. These must remain alive throughout gameplay.
3. Only **after service readiness**, construct the game environment. In 142 recorded launches, the executable is `bin64_SteamRetail/Evolve.exe`, the working directory is the same folder, the argument string is empty, and the recorded Steam fields are `SteamAppId=273350`, `SteamGameId=273350`, `SteamOverlayGameId=273350`, with `STEAM_COMPAT_DATA_PATH` unset on Windows.
4. Provide additional session-specific runtime settings to the game-side hook. The client assembly references `MODDED_EVOLVE_STAGE2_FRONTEND`, `MODDED_EVOLVE_STAGE2_CATALOG`, `MODDED_EVOLVE_STAGE2_LOG`, `MODDED_EVOLVE_STEAM_EMU_DLL`, the relay/identity variables and other state. Values **must be generated by a real active service host**; don't hard-code fake tokens, IDs or URLs.
5. Create `Evolve.exe` suspended, allocate remote memory, write the **Stage2Trace.dll** path, run the original loader in the target, confirm a successful load and only then resume the primary thread.
6. Maintain profile/Steam compatibility services and independent original-file restoration until the game exits.

`ModdedEvolveSteamCompat.dll` and `Stage2Trace.dll` are **not** equivalent to process parameters; the client initializes them and exposes services. The supplied .NET launcher advertises smoke-test flags but no verified production service-only mode. Do not assume `--stage2-smoke --no-launch --keep` provides a durable supported background service host; its embedded status text says no-launch stops there.

The executable-file preflight no longer substitutes for runtime readiness. The actual worker starts the independently supervised client services, waits for its runtime handshake, then verifies the new Stage2Trace and SteamCompat hook logs. Port ownership and file existence alone are not confirmation of gameplay functionality.

**Never commit or copy the uploaded personal certificates, DPAPI identity files, profile records, secrets, relay tokens or extracted client archives to this public repository.**

# Direct Launch and Client Launch

## Selected launch mode

**Client Launch is the default for new or unspecified settings** because it runs the original launcher and preserves the real relay, authenticated profile and Shift+Tab friends overlay. An explicitly saved Direct Launch preference remains unchanged for testing. In **Settings → Game Storage → Set Up Manager**, choose Client Launch or experimental Direct Launch. Both Home Play buttons use the selection:

| Action | Direct Launch (experimental) | Client Launch (default) |
| --- | --- | --- |
| Play without Mods | Verify the game, refuse unresolved original backups, restore normal manager network policy and start `Evolve.exe` as the interactive standard user with original game PAKs | Launch normal `ModdedEvolveLauncher.exe` as the interactive standard user, keeping its repair and profile services |
| Play with Mods | Build/sign enabled projects, prepare and verify the reversible journal, swap custom-signed PAKs and `inject.dll` **before** process creation, arm independent rollback watchdog, then start `Evolve.exe` directly | Keep established Frida `CreateProcessW` interception and client-owned process launch, signed PAK swap, and watchdog |

The Direct Launch button is no longer separate. Both Play buttons use the setting. Switching to Client Launch never erases signing-stage backups or rewrites an active journal. The shipped client's `--stage2-smoke --no-launch --keep` path does not initialize the normal launcher relay control, authenticated social profile and overlay endpoint, so Direct Launch is not the recommended online route. The client-owned CreateProcessW interception remains available to swap only enabled-profile PAKs. When it sees the game being created it records a read-only 2000/2002 loopback connectivity snapshot without copying, creating, or logging session credentials.

Direct mode does not require a client executable just to save the game path, build a new signing stage, or run either Play action. Existing Client Launch setups remain supported. Direct startup uses the verified Explorer medium-integrity desktop token (not the manager's elevated administrator token), game binary working directory and the three Steam app-ID environment fields logged by the client. Direct mode uses a separate `direct_standard_user_launch.py` helper rather than overwriting any existing client token broker.

## Recovery

The verified sign/cache preparation runs while game and launcher processes are closed. A direct modded launch revalidates the original/staged file mapping, prepared sizes/digests, and recovery ledger. It records `swapping` **before** any same-volume rename and `swapped` after the final PAK. No launcher pause or Frida hook is needed.

A partial swap attempts immediate recovery through `reusable_restore.py`. After a completed swap, `auto_restore_watch.py` runs in its own detached process and restores originals when the game exits, even if the manager quits. Startup and watchdog failures preserve backups/journal and report recovery actions. Do not launch again if the journal is still active.

## Online/runtime limitation

**Native process creation does not reproduce client services.** In Direct Launch, the current prototype does not implement Modded Evolve local profile/auth endpoints, Stage2Trace game bootstrap, or the full Steam compatibility relay lifecycle. Evolve's process may start without a usable profile or connected services. Successful PID reporting does **not** establish game-playable or online parity. Neither the manager nor this PR modifies the server or claims it can bypass authentication.

Client Launch remains available for cases requiring the existing client runtime. Direct Launch should be validated on an interactive Windows desktop, separately for clean and modded sessions, before releasing to general users.

## Home banner artwork

The supplied `default_loading.dds` is intended as the large Home banner, **not** the application's loading screen. Home reads DXT1/BC1 `assets/default_loading.dds` next to the manager executable (or `default_loading.dds` alongside it), darkens it for readability, and retains usable controls when the file is absent. The DDS is **not yet packaged** in the PR; installer packaging remains a required follow-up before release.

## Verification

- Run Rust/Windows CI, Python direct-launch ordering/regression tests, and install/update tests.
- Launch unmodded Direct Launch with original PAKs; confirm executable working directory, medium integrity and unmodified original files.
- Launch modded Direct Launch with one known-good locally signed PAK; confirm actual game content mounts and all originals return after exit.
- Kill the manager while the game runs; confirm the detached restore watchdog still completes.
- Inject pre-launch swap, game-creation and watchdog failures in a throwaway test installation; inspect recovery logs and verify no original is overwritten or abandoned.
- Compare Stage2Trace, SteamCompat and profile-service initialization with a known working Client Launch session; do not infer network compatibility from process creation alone.

## October 15 Stage2Trace.dll update (PR #94)

The user supplied `Stage2Trace(5).dll` (2,217,472 bytes), dated October 15, 2026. It has SHA-256:
`a0219d94b3c7ec4d73999b531adbbf13aa595bf39babc9e7810a1cf6db0d1067`.

The bundled September 12 DLL has a **different** SHA-256:
`e4a1c81e1970de697b271b3756f79040b82633fe4569c3a65bb20787cfa5be5c`.
The new contract **does not silently substitute** that older DLL. The October build is expected to be installed locally as `bin64_SteamRetail/Stage2Trace.dll` (do not retain the upload's `(5)` suffix). These user-supplied executables are **not committed** to this public repository.

The working game's Stage2 hook logs confirm `ModdedEvolveSteamCompat.dll` loads from **beside Evolve.exe**, not from the shadow client service folder. The compatibility provider file at that location is checked against the known uploaded or original-client provider revisions. The manager will not silently replace a mismatched game DLL or delete a previous copy.

`MODDED_EVOLVE_STAGE2_CATALOG` points at a **real nonempty file** under the interactive user's LocalAppData:
`ModdedEvolveLauncher/stage2/ownable-catalog-launch.txt`.
It must be generated by the running client service host, not replaced with `Assets/stage2` or a sample catalog.

The new DLL consumes the `MODDED_EVOLVE_STAGE2_MODES` variable and includes additional arbitration and lobby flags. A verified October 26 working run used:
`Stage2ArbitrationComplete,Stage2ArbitrationTrace,Stage2Listener,Stage2LobbyTaskDataBridge,Stage2LobbyTaskMap,Stage2OwnableCompat,Stage2OwnableVtableCompat,Stage2ProfileCompat,Stage2ProfileOnly,Stage3GameContextTrace,Stage3NativeListen,Stage3RouteObjectTrace`.
The manager must use **live client-advertised values** (not hardcode an old minimal profile-only list).

The runtime environment builder now refuses unrecognized, empty or malformed session values instead of setting blank relay/identity parameters. It understands the new `MODDED_EVOLVE_STAGE2_COMMUNITY_NEWS` as an optional client-supplied setting, without fabricating a path.

The game-side trace should report all of the following before direct launch is considered successful:
`Stage2Tracer starting;`, `STEAM_EMU active provider=<verified game-local DLL>`,
`Modes from MODDED_EVOLVE_STAGE2_MODES: <verified modes>`, and
`Hooks enabled status=MH_OK`. The hook log must be newly truncated before each game launch, so stale results cannot count.

**Important:** Direct Launch can now be exercised on Windows using the selected new DLLs. The pinned .NET service-only host adapter and session handoff have **not passed a real Windows game test**, so successful game startup/profile functionality is not guaranteed. The worker stops on concrete runtime failures. For modded tests, only an already verified original-file backup/journal can be modified, and failed partial swaps are handed to the existing restoration helper after the service host exits. Never retry modded launch over unresolved original-file backups.
